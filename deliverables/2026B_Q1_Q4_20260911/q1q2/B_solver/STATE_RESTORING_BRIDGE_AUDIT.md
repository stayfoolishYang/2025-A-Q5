# State-restoring bridge 只读审计

审计日期：2026-09-11。结论：**STOP，不实现恢复桥，不新增场景测试。**

在现有四动作接口中，没有可执行的纯移动。提前清除后真回到原 MEC 中心，必须付出额外测量或清除动作费用；即使假设存在免费发起的纯移动，segment 返回 MEC 也恰好耗尽之前节省的路程，NCCP 通常还会绕路。直接接原下一动作可以讨论较弱的决策状态耦合，但当前执行流程没有冻结该原动作，且时钟、日志和预算不因此恢复相等。这不足以支持本任务要求的严格状态恢复与耗时不劣保证。

本次只阅读 Solver、Client、本地 Engine/HTTP 协议及相关规划代码，未调用模拟器、未运行求解器或测试。默认 MEC、NCCP 参数、Q4 的 45 个发现节点及覆盖构造均未修改。审阅对象是现有本地恢复引擎和客户端实现，不能把这些结论扩张为未审阅的官方服务内部实现。

## 1. 审计中的“同一状态”

比较同一证书成立的时刻：机器狗位置 x，目标频道 c，硬域 Ω，原 MEC 站位 M，以及提前清除的安全站位 q。假设真实源仍在 Ω，M 与 q 都已通过严格提交坐标认证，两处清除均成功。

原执行是在 M 清除，随后继续原程序；候选执行是在 q 清除，随后试图恢复原状态。至少要区分以下三种结论：

| 层次 | 必须比较的内容 | 不能省略的限制 |
|---|---|---|
| 严格完整状态相等 | 物理位置、接收频道、已清集合、Engine 虚拟微秒、终止状态；Solver 历史/硬域/粒子/RNG/调用栈及待执行路线；动作日志与 HTTP 会话状态、真实剩余预算 | 改变清除坐标已经改变日志；节省虚拟时间意味着时钟不相等。只把某个 `position` 变量改成 M 不构成物理状态恢复。 |
| 未来决策状态相等 | 会影响之后策略和观测的状态相等，明确排除只作审计的日志和成本累积量 | 排除项必须明示，且当前程序不得把它们用于决策；预算终止仍有实际语义。 |
| 带成本优势的耦合关系 | 决策状态相同，同时候选虚拟成本不大于原成本，未来动作及观测能够逐步对应 | 这是状态之间的关系，不是时钟相等；还须处理逐动作取整、超时和真实运行预算。 |

本报告不通过改名把第二、三种关系宣称为第一种。

## 2. 真实动作及状态语义

接口由 [Client.action](/I:/GithubRick/2025-A-Q5/B_solver/simulator.py:26)、[protocol.ROUTES](/G:/QQ/jammers_linux/protocol.py:11) 和 [Engine.apply](/G:/QQ/jammers_linux/engine.py:160) 三层共同限制。允许的机器人动作只有 `/enter`、`/measure`、`/clear`、`/exit`。

| 动作 | 位置与频道 | 固定虚拟费用及其他作用 |
|---|---|---|
| `/measure(p,c)` | 先到 p；将接收频道改为 c | 5 s；不同频道另加 1 s；产生观测。Solver 会追加频道历史，必要时更新硬域、粒子和 RNG；near 会立即触发一次清除。 |
| `/clear(p,c)` | 先到 p；**不改变接收频道** | 成功 5 s，失败 3 s；成功将 c 加入已清集合。Solver 删除对应 track，增加清除计数并更新日志。 |
| `/enter` | 不执行移动 | 已进入会话不能再进入；不是状态重置。 |
| `/exit` | 不执行移动 | 结束会话，不是零成本移位或暂停。 |

Engine 每次移动增加整数微秒 `go_round(1e12*hypot(delta)/5_000_000)`，对应 5 m/s、逐动作就近取整；达到 360000 s 会终止。见 [移动和动作计费](/G:/QQ/jammers_linux/engine.py:181)。不存在跳过测量/清除固定费用的移动标记。

对刚清除的同一频道再 `/clear(M,c)`，Engine 的 `available` 为假，必为失败清除，仍花费移动时间和 3 s。它不改变接收频道，但会多出一次动作、清除尝试和日志。对已清频道再测量必得到 `no_signal`，仍花费 5 s 及可能的切频费用；经 Solver.measure 调用还会追加历史。直接绕过 Solver 调用 API 也不能免除 Engine 时间和会话记录。

HTTP 服务在 [Session.execute](/G:/QQ/jammers_linux/server.py:166) 维护 request-id 缓存、动作序号、计数和日志。同一 request-id 与相同请求只返回缓存响应，不再执行；同 id 改坐标会冲突。它不能充当回滚或移动命令。Client 对接受响应更新本地位置，但擅自改写这个缓存位置只会造成客户端与 Engine 不一致。

## 3. 真返回 M：没有可保留的几何收益

原路径的移动长度为 `|x−M|`；提前清除后再回 M 的移动长度为 `|x−q|+|q−M|`。三角不等式给出

\[
|x-q|+|q-M|\geq |x-M|,
\]

等号恰在 q 位于闭线段 [x,M] 时成立。

因此，在假想纯移动接口下：

- segment 站位若精确在线段上，回到 M 后的总移动与原方案相同，之前的局部节省已经全部用来完成余程；没有正的总路程收益。
- NCCP 只最小化 `|x−q|`。若 q 不在 [x,M] 上，绕 q 回 M 严格更长；最近可清点的性质不能改变该结论。
- q=M 是原 MEC 操作，本来就没有提前清除收益，也无需桥接。

在真实四动作接口下，只要 q≠M，回到 M 至少要再发一个带位置的动作。使用已清频道的额外 clear，理想连续计费下

\[
T_{\rm bridge}-T_{\rm original}
=\frac{|x-q|+|q-M|-|x-M|}{5}+3\ \mathrm{s}\geq3\ \mathrm{s}.
\]

额外 measure 的固定损失至少为 5 s，并可能有其他副作用。微秒取整不可能挽救这一秒级固定损失。完整状态中的时钟、动作计数及日志也无法恢复成原值。此处已经足以拒绝“实际返回原 MEC 状态并不劣”的实现。

## 4. 直接接原下一动作：能证明什么，缺什么

设原 MEC 清除完成后，原程序下一条带位置动作是 `(path,y,channel)`。如果该动作已经固定，并且两方案都执行它，则精确在线段上的 segment 点满足

\[
|x-q|+|q-y|\leq |x-M|+|M-y|.
\]

这不需要先返回 M，也不多发动作。它是有效的两段几何结论；一般 NCCP 不享有该结论。若下一条是 `/exit`，没有下一位置可供恢复，最多保留末次清除的局部收益。

本地 Engine 有利于建立**条件性的较弱耦合**：源位置和朝向静态；测量误差由固定 noise seed、频道和坐标确定，[bearing_error](/G:/QQ/jammers_linux/engine.py:41) 不消耗按动作推进的随机流，也不依赖虚拟时间。清除不改接收频道。于是若双方已清集合一致、同一 y 和动作频道确实被执行，且没有预算终止，观测内容/清除结果相同，执行后物理位置和频道也相同。

但还必须同时满足以下条件，才能进一步讨论之后的决策状态：

1. **保留原 continuation。** [Solver.run](/I:/GithubRick/2025-A-Q5/B_solver/solver.py) 在清除返回后按当前位置比较定位与发现费用。定位候选、diagnostic 和 fallback 排序也使用当前位置。让原程序直接从 q 继续，不能保证下一动作还是 y。待访问 `nodes`、for/while 的当前位置、诊断返回路径及已生成的 fallback 路线也属于 continuation，单存一个 M 不够。
2. **同一历史和 RNG 推进。** [Solver.measure](/I:/GithubRick/2025-A-Q5/B_solver/solver.py) 为每频道保留观测，Hypotheses 的 [update](/I:/GithubRick/2025-A-Q5/B_solver/particles.py:60) 在重采样时推进独立 RNG。若不增加观测、同样历史得到同样下一响应，原则上可匹配；额外测量或重新规划造成不同观测就不能这样推断。Engine 的位置噪声无状态，不等于 Solver 没有 RNG 状态。
3. **真实成本与规划位置分离。** 若让策略暂以 M 规划、实际却从 q 出发，需要明确记录两种位置及真实移动费用，不能把 `api.position=M` 当作已经移动。现有 `Solver.clear/measure` 和 EngineAdapter 均按当前位置记路程，修改它们已经超出“原函数后补一步”的范围。
4. **采用整数微秒门禁。** 两段连续距离不劣不自动推出两次取整后的总微秒不劣；例如两段未取整费用由 `(2.4,2.4)` 微秒变为 `(1.6,3.2)` 微秒，总连续费用相同，取整总量却由 4 变为 5。将来若研究较弱耦合，必须按实际提交坐标和 Engine 相同算式比较完整动作费用，不能只使用浮点距离总和。
5. **不混同虚拟和真实时钟。** 当前策略主要用位置/几何费用，而非累计虚拟时间选择动作；但 Engine 会按累计时间结束。较低虚拟时间可形成预算优势，仍不是状态相等。Client、EngineAdapter 和 HTTP Session 另有真实 1200 s/窗口期限；额外规划或桥接请求不能证明现实耗时不增加。日志时间戳、request-id 缓存也不会回到原状态。

所以，固定 y 后有条件证明物理状态和若干决策输入重新相同，是可能的；本审计没有把它错误判为数学上完全不可能。可是这需要明确的原策略 continuation 与成本支配协议，当前代码并未实现，完整状态也仍不相等。已有 8984 个快照中的固定 y 两段结果是离线反事实核对，不提供在线锁定 y 或状态恢复的实现证据。

## 5. 停止边界与下一步范围

**停止实际返回 MEC 的 bridge 路线。** 其动作接口与成本阻碍已确定，不需要花满 30 分钟，也不值得用新案例重复验证三角不等式。没有新增桥接参数、双位置状态、重放控制器、纯移动伪接口或异常恢复逻辑。

“从虚拟原站位规划并锁定下一真实动作”可作为另一种策略研究，但不能沿用严格恢复桥名称或旧性能证据。本任务不建议立即实现它：它需要新的调用链与日志语义，收益仍有取整、预算及最后动作边界，尚不足以支持整体不劣承诺。当前保持默认 MEC，把下一轮独立消融留给既定 Q4 调度；本文件不更改该路线。

对并行 Q4 调度方案，另有两条只读风险提示：

- 原路线是开路径，存在中途定位打断。即使刷新后完整剩余开路径更短，也不能证明首跳、前缀或最终整局更短，仍应独立配对消融。
- P4 在一个节点的全部未清频道扫完后才重新竞争定位，仅 near 会立即清除。若保持当前频道优先、全部未清频道各测一次，unknown-first 通常不减少该节点测量数或切频数；其重要作用可能是改变结束频道及后续诊断费用。不能把较早看到某频道等同于立即开始定位。
