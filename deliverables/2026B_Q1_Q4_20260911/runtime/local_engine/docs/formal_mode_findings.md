# 正式模式能否通过客户端还原种子

**本轮已查清客户端正式场景的载入方式，但没有找到可据此恢复正式生成种子的方法。** 正式模式接收加密场景包，完成解锁后直接解析完整场景。正式场景格式还明确要求生成器版本、生成种子和生成规则为空。因此，当前 EXE 所提供的证据不足以恢复服务端原先怎样生成这些场景，也不能证明正式生成算法与演练相同。

分析对象为此前用户提供的 `jammers-simulator.exe`，SHA-256 为 `2373b9e7af83735a04309e2983eb433ec46faf7e0b8494410ce7fded2a297c27`。本轮为静态分析；未运行原程序或其函数，未请求服务器，未启动正式测试。下述地址仅适用于这一指纹的版本。

## 1. 这次比此前多确认了什么

此前证据主要是：`StartPractice` 直接调用 `GeneratePractice`，而正式启动函数中没有发现这一直接调用。仅凭这一点不能排除接口间接调用。

本轮补查了 20 个函数、实际 Go 接口方法表、运行时对象的装配，以及解锁结果如何传入解析器。现在支持结论的证据是“正式流程实际怎样使用场景”，而不只是“没有搜到某个函数名”。

| 问题 | 本轮结论 | 证据性质 |
|---|---|---|
| 正式客户端是否收到场景包？ | 是，准备响应含 `sealed_case_package_b64` 与其摘要 | Go 类型字段和解码调用 |
| 解锁后得到的是种子还是场景？ | 数据直接传给 `scenario.ParseAndValidate` | 实际调用及寄存器数据传递 |
| 正式场景是否携带生成种子？ | 校验要求 `generator_seed_hex` 为空 | 正式来源分支的指令检查 |
| 正式和演练是否使用相同的服务端生成算法？ | 尚不能判断 | 服务端实现未提供 |
| 是否取得真实正式场景或破解解密？ | 没有 | 本轮只有本地静态证据 |

## 2. 正式流程中的场景来源

1. `remoteapi.(*Client).PrepareFormal` 的响应对象包含 `sealed_case_package_b64`、`sealed_case_package_sha256`、`case_code` 等字段。函数解码场景包、核对摘要，并交给 `FormalCaseVerifier.Verify`。
2. 激活请求包含客户端的解锁公钥；激活响应包含 `case_unlock_envelope_b64` 和 `activation_ticket_b64`。这与场景生成种子是不同的概念。
3. `recovery.(*RuntimeStore).CommitFormalActivation` 先检查激活材料，再调用 `packagefmt.UnlockFormalCase`。
4. 解锁成功后的返回字节直接传给 `scenario.ParseAndValidate`。之后继续检查问题编号和来源，来源必须为 `formal_dataset`。
5. `startActivatedFormal` 将已解析的场景交给 `simcore.NewEngine`，或在恢复流程中调用 `NewEngineFromState`。

核心证据：

| 地址 | 已核对的动作 |
|---|---|
| `0x1404ccc41` | 对准备响应中的场景包进行 Base64URL 解码 |
| `0x1404cd081` | 调用 `FormalCaseVerifier.Verify` |
| `0x1407297c0` | 调用 `UnlockFormalCase` |
| `0x1407298bb` 至 `0x140729940` | 成功路径保留返回字节的指针、长度、容量，并传给场景解析器 |
| `0x140729940` | 调用 `scenario.ParseAndValidate` |
| `0x140729a34` 至 `0x140729a58` | 检查来源字符串为 `formal_dataset` |
| `0x140751798` | 将场景交给 `simcore.NewEngine` |

接口绑定也已检查：`desktopapp.NewRuntime` 使用的接口表分别指向真实的 `auth.Manager`、`remoteapi.Client` 和 `recovery.RuntimeStore` 方法。其中 `StartFormal` 的准备调用在 `0x14074f2d4`，激活调用在 `0x140750597`，提交激活材料调用在 `0x140750c45`。这些是接口间接调用，不能只查直接调用索引。

对应方法表及完整目标地址保留在 `evidence/interface_bindings.json`；其他间接调用仍单独记录，不宣称全部已解析。

## 3. 正式格式明确禁止生成器元数据

从原 Go 类型元数据得到以下字段偏移：

| 字段 | Scenario 内偏移 | 演练 `practice_generated` | 正式 `formal_dataset` |
|---|---:|---|---|
| `dataset_version` | 56 | 必须为空 | 必须是合法、非空的数据集版本 |
| `generator_version` | 64 | 必须为 `practice-gen-v1` | 必须为空 |
| `generator_seed_hex` | 72 | 必须为 64 个小写十六进制字符 | 必须为空 |
| `generation_rules` | 96 | 必须与默认演练生成规则一致 | 必须为空 |
| `noise_seed_hex` | 80 | 必须为 16 个小写十六进制字符 | 同样必须提供 |

在 `Scenario.validate` 中，栈上 Scenario 起点为 `rsp+0x1e8`。正式分支在 `0x1404f194e`、`0x1404f1959`、`0x1404f1964` 分别检查上述偏移 64、72、96 的指针是否为空；不符合则返回：

```text
formal scenario must not contain generator metadata
```

此错误字符串位于 `0x140823836`，长度 51。不是根据字段名称猜测，而是字段偏移、分支指令和报错信息三者相互印证。

**这意味着客户端正式场景本身不提供“生成种子到场景”的重放信息。** 但它不证明服务端从未使用过随机种子：服务器可能随机生成后移除元数据，也可能使用筛选、固定数据集或其他方式。具体是哪一种，本次没有证据。

误差场种子仍然存在，是因为本地引擎需要据此计算测量误差。不能把它当成干扰源坐标、频道和类型的生成种子。

## 4. 能否靠解密拿到正式生成算法

已确认解锁相关代码调用 X25519 密钥协商、HKDF 和 AES-GCM；正式场景包还会经过 Ed25519 签名验证。正式启动过程中有运行时生成密钥的调用，激活响应提供解锁包。

| 作用 | 指令证据 |
|---|---|
| 启动时生成 X25519 密钥 | `0x14074f615` |
| 解锁时进行 ECDH | `0x1404c1e87` |
| 派生解锁用密钥 | `0x1404c21c5` 调用 HKDF |
| 构造 AES 与 GCM | `0x1404c2793`、`0x1404c27a7` |
| 验证场景包签名 | `0x1404c0ab8` 调用 `ed25519.VerifyWithOptions` |

以上证明了程序采用这些机制，**不等于已经完成密码实现安全审计，也不等于已找到绕过办法**。本轮没有真实正式场景包、对应解锁材料或服务端源码，未尝试解密真实正式任务。

即使通过原程序正常取得某个场景的明文，得到的也是这一个场景的数据；按照上述格式，它仍不携带生成器元数据。不能从“解出一局”直接推出“还原了服务端生成算法”。

## 5. 对离线训练有用的新确认

正式和演练的来源检查之后会汇合到同一段合法性校验，而且都要求同一套默认仿真规则。因此下列约束可以从客户端进一步确认：

- 干扰源数量为 10–16。
- 频道为 1–20，按严格递增顺序排列，不能重复。
- 接收半径为 1000–1500 米。
- 干扰源坐标都必须位于半径 1770 米的圆盘内。
- Q3 不允许定向源；Q4 至少有一个定向源。
- 两种来源都必须提供合规的误差场种子和默认仿真规则。

其中坐标约束的证据是公共分支 `0x1404f144a` 调用 `insideJammerDisk`。后者在 `0x1404f1aef` 使用常量 `0x69800e80 = 1770000000` 微米，并通过整数平方和判断圆盘边界。

这比此前“仅确认演练生成器采用 1770 米圆盘”的证据更进一步：**这一版本客户端接受的正式场景也受该约束限制。** 但均匀分布、独立采样、各类困难场景出现频率等，仍然不能从合法性条件推出。

因此，按还原演练生成器训练是有依据的；为覆盖正式场景的不确定性，还可以在这些已确认约束内构造边界、聚集、定向覆盖不利等压力场景。应将其标为自建压力测试，不能标为复现正式种子。

## 6. 当前还原边界与后续可行路径

**可以还原的部分：** 客户端场景格式、来源约束、加载与仿真行为，以及此前已恢复并对照过的演练生成算法。

**当前缺少的部分：** 正式数据集最初的生成实现、生成参数分布、原始生成种子和真实正式场景样本。继续反编译客户端不能保证得到未包含在客户端中的服务端信息。

进一步判断正式与演练生成算法是否相同，需要官方公开的生成说明、可核验的服务端实现，或有来源依据的测试数据。仅有编号或少量输出通常不足以唯一确定生成过程。本轮没有找到把测试编号转换成正式生成种子的依据。

本报告不改变此前的交付状态：新的演练生成器是独立还原包，最初离线模拟器的默认生成入口尚未由本线程替换；正式载入机制的还原也不是一次模拟器升级。

## 7. 可复核材料和验证范围

`collect_evidence.py` 已对指定 EXE 实际执行，完成 SHA-256 检查，提取 20 个函数及 5 个结构体的字段，并验证关键地址、错误字符串、接口方法表和半径常量。产物保存在 `evidence/`。

这属于静态提取与核对，不是正式运行验收，不包含任何成功解密或正式测试成绩。先前 518 个种子的整函数对照只适用于演练生成器，不能用于证明正式算法一致。
